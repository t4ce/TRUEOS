How to read the architecture

One coordination model, two execution engines is a useful proposed architecture. Today, CPU guest execution uses executor-backed VMX carriers, and GPU work uses mediated capabilities plus driver / firmware execution. The GPU admission executor is host-side code; it does not run the EU math. Odin's compiler runs on the CPU, even when generating GPU code.

The CPU side already contains vCPU-like state. Its representation is distributed across guest registers, VMCS/EPT, VM identity, run generation and lane assignments. A carrier lane is the host resource that runs this state; a stable logical vCPU identity could be documented or factored above it. A full public multi-vCPU model, migration policy or unified scheduler is not established by this review.

There are also two GPU ABI layers to keep distinct: a complete scalar-call kernel and a pixel arithmetic body with a runtime-owned envelope. Their active-lane and result conventions differ. The legacy boids DSL adds a third historical route. These are not interchangeable meanings of “two runtimes.”

Current integration gap: odin-son still emits trueos_cabi_vgpu_call_f32_v1 with a pointer-based signature. Current TRUEOS rejects that import as retired and exposes the handle-based trueos_cabi_vgpu_scalar_f32_v1. This static finding does not invalidate the separate recorded pixel-body execution. No runtime implementation was changed for these diagrams.

What the recorded GPU run establishes

The checked-in 22 October report records ADL-S execution of runtime-compiled Mandelbrot bodies with matching independent image hashes. The 25-iteration body is 14,496 bytes and the 16-iteration body is 9,168 bytes. It establishes this bounded generated-code path. This review did not run the rig, establish a speedup, or prove arbitrary Odin programs on the GPU.

The encoder deliberately emits uncompacted 16-byte instructions. Its SIMD8 arithmetic already operates on vector registers. Pixel input contains eight independent coordinates; the scalar-call ABI exposes one active result lane. A native instruction's byte length alone cannot determine program size limits, useful parallelism, or CPU/GPU performance.

Batching and the “one submit” objective

The current pixel driver loops over row batches, submitting and polling each batch. One application render call therefore does not imply one hardware submit. A future resident worklist could reduce host crossings, but requires device memory operations, bounded descriptors, dependency rules and a termination/completion protocol beyond the current arithmetic-only body.

For performance work, record compilation, admission, mapping / visibility, queueing, submit, execution, retirement and acquisition separately. Compare identical workloads against a vectorized CPU baseline. Long GPU sequences can amortize overhead, while register pressure, divergence, code expansion and independent work supply determine throughput. Matrix instructions are a separate feature to establish and validate; they are not shown as available in this target.

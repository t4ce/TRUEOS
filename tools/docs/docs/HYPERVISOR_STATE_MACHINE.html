Filesystem behavior

what app developers actually see

Persistent files live outside the VM snapshot.

The Blueprint starts with its app root as HOME, PWD, and process CWD. Standard filesystem calls are rerouted to TRUEOSFS; the preferred direct SDK surface is operation-based and asynchronous.

Pause does not copy files. A future clone gets no automatic mutable-data copy. Decide at PreparePause: copy selected files, write an app checkpoint, share immutable data, or begin empty.
Developer contractv2 async FS
01
Use paths, not immortal handlesLong-lived file handles and in-flight writes must be closed or cancelled before Ready.
02
Keep the Blueprint lane cooperativeStart an operation, poll lightweight status, read results in bounded chunks, then discard the operation.
03
Treat assets and mutable state separatelyPackaged asset paths are written into the app root at fresh admission. Do not keep user edits at those same paths; use a workspace or apps/common by explicit policy.
04
Use named roots for concurrencyOnly one running/paused default instance is allowed. Additional named/peer instances receive isolated GUID-qualified directories.

Pause boundary

what is state vs. capability

Retain locally; snapshot deliberately; rebind reality.

A cooperative pause retains the quiesced VM in memory without writing the checkpoint store. snapshot <vmid> uses the same PreparePause → Ready boundary and then commits a warm snapshot v5 under that VM ID. Numeric handles to host resources are never portable state; release them before Ready, then recreate them after that exact call returns on Resume.

ResourceAt ReadyAfter Resume
Heap, stack, GPRs, RIP/RSPretain / snapshotContinue after boundary

Current boundary: pause <vmid> resumes the retained same-slot VM directly; load <vmid> restores the last committed snapshot. Peer offers include committed snapshots only. Cross-slot and cross-host clone/restore remain disabled because guest-writable heap pointers and allocator mappings are not yet relocatable.

OP_BP_LIFECYCLE_IDENTITY		PAUSE/SNAPSHOT arm a host request; the app polls an operation ID, deadline and reason. Its matching READY(operation, checkpoint_version[, app_payload]) selects Pause or Snapshot disposition at the exact VM-exit boundary. Same-Hull resume returns after that call. Live update instead starts a fresh Hull and lets the app consume its compact payload once through CHECKPOINT_RESTORE. The restored identity retains instance and lineage while advancing generation.
Warm is RAM, named is disk. The per-VM checkpoint store is an in-memory immutable Arc image. A warm snapshot or preserve therefore survives only while the host stays up. Only store <vmid> <name> creates the TRUEOSFS envelope that can survive reboot.
Live update is application replication. For a payload-capable Blueprint, the reversible phase may keep an exact warm snapshot in the old kernel for abort recovery, but the disk handoff is a compact *.trp envelope containing only relaunch metadata and the app checkpoint. The candidate never restores old VMCS state, Hull memory, or guest-heap pointers. Pre-update running/paused policy is preserved after the fresh launch.

Current working-tree audit

contract mismatches requiring an implementation decision

Do not treat these as settled lifecycle semantics.

Expected contractCurrent working-tree behaviorWhy it matters
PreserveMode::Stop means checkpoint then terminal teardown; only PreserveMode::Pause owns retained lifecycle state.snapshot_on_preserve_exit now sets pause_latched and suspends the Blueprint process context after any successful preserve, including Stop. Teardown consequently retains launch/process context.The enum documentation, VMX-shell help, and the main diagram's preserve path still say “stop.” The implementation currently turns a successful preserve into a retained warm state. This is the exact semantic fork under review, not a documented contract.
A plain cooperative pause can directly resume the exact in-memory continuation.VM exit updates VM_SNAPSHOT_META, while start_with_mode requires VM_RESTORE_META whenever pause_latched is set. Ordinary pause does not populate that restore meta. After a prior load, it can instead retain an older restore meta.Fresh pause/resume can reject with GuestMemoryUnavailable; Load → Pause → resume risks using stale restore state. The direct-resume edge in the diagram is therefore the intended model, not yet a proven implementation invariant.

# TRUEOS driver and application services

[Overview](runtime-inventory.md) · [Task declarations](runtime-task-index.md)

This inventory covers `src/**` outside the runtime/service layer `src/r/**`, workers, chronos, spirit and core SMP/executor machinery, which are described in other sections. All declarations below are repository-owned; vendor implementation bodies were not searched. There are **91 task-attribute declarations in this source slice: 90 kernel-source declarations plus one uncompiled turbo reference overlay**. Attribute-less service loops and resource pools follow the task table. Source references identify the declaration attribute line; function definition follows it.

**Status interpretation:** boot means statically wired into startup, not observed running; conditional means readiness/hardware/feature/policy may prevent admission; on demand means a source caller creates a token after a command, device or guest request; no incoming startup means no token call/entry found in this audit, not a compiler proof of dead code. `#[task]` defaults to one storage slot. Task pool storage is a maximum simultaneous task-instance count, not a CPU count. Registry references in short form refer to [src/r/services/spawn_service.rs](../../src/r/services/spawn_service.rs).

The default feature set ([Cargo.toml:85](../../Cargo.toml#L85)) includes H264 encoding, task profiling, and odin native GPGPU. It excludes `trueos_lumen`, `trueos_ttstt`, and `legacy_vm_checkpoint`; configurations used by external build scripts may enable them.

2. **Disconnected start helpers:** USB media-control task ([src/usb3/hid/mediacontrol.rs:147](../../src/usb3/hid/mediacontrol.rs#L147)) and LED task ([src/usb3/hid/leds.rs:422](../../src/usb3/hid/leds.rs#L422)) have token calls, but all such calls sit inside `maybe_start_media_control` / two `maybe_start_led_controller*` helpers with **no source caller**. This is why nonzero lexical symbol references do not prove use.
3. **Explicitly disabled:** `tga_task`, `raple_service`, and Intel HDA audio demo have startup wrappers, but registry disables them (`spawn_service.rs:1600/:1772/:1778`). 4. **TTSTT controller/pool currently not started by an audited path:** Feature absent by default; with feature enabled, warm flag is false (`allcaps.rs:108`). 5. **Optional reference code:** [src/turbo/trueos-lumen-cpu-vnni/reference/lfm25_boot_warm.cpu_vnni.rs](../../src/turbo/trueos-lumen-cpu-vnni/reference/lfm25_boot_warm.cpu_vnni.rs) is not a compiled module; current warm task exists in [src/ai/lfm25_boot_warm.rs](../../src/ai/lfm25_boot_warm.rs). 6. **USB second-controller event-pump capacity:** `MAX_CRABUSB_CONTROLLERS=2` (`usb3/mod.rs:24`); each successful `run_usb_controller` attempts `usb_event_pump_task` (`:173`), but its `#[task]` declaration (`:459`) has singleton storage. With two concurrently alive controller pumps the second allocation can fail, log and return (`:176–181`). This follows from static capacity and control flow; no two-controller runtime test was run.
7. **Boot-wired can still idle or exit:** Codex prompt waits on signal while closed, GPGPU preview/SVG endpoints wait for explicit start, screenshot waits for capture demand, H264 waits for sessions. Hardware startup can return when admission fails. They have real caller/consumer paths; “idle” is not evidence of dead code or runtime residency.

## Audit method and limits for this inventory

- Enumerated `#[trueos_executor::task(...)]` and imported `#[task(...)]` attributes over owned Rust files, retaining all 91 declarations including the reference overlay. Traced function/token names to source callers, central startup wrappers and TaskSpec states, then read helper call chains to reject lexical-reference false positives.
- Searched spawn APIs (`Spawner`/WorkerSpawner, `spawn_and_wake_remote`, `spawn_local_detached`, blocking jobs, C ABI thread/pump exports), and function/type/static names containing task/service/worker/pool. Inspected module/path/include boundaries, Cargo feature defaults, readiness gates and policy constants.
- Distinguished task-frame storage, CPU carrier leases, logical WLS identities, network/device queues, GPU contexts, buffers and memory table pools. Most hardware queues are resource owners, not software task pools.
- This is a static source audit. No boot trace, task-profile snapshot, runtime hardware enumeration, linker map or whole-program/cfg-expanded call graph was available. No claim here proves a task was scheduled on the user's hardware. ABI/plugin/guest/external build references may exist outside the non-vendor scope; dynamic dispatch, callbacks and macro expansion can hide edges.
- Source lines are for the audited working tree and should be regenerated if files change. No kernel or crate implementation was changed by this analysis.

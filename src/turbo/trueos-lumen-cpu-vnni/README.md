# TRUEOS Lumen native-Q8 AVX-VNNI integration bundle

This bundle switches the fixed LFM2.5 Lumen projection path from the in-place
Q8x16 iGPU image to a CPU backend that reads the sealed **native Q8_0 row image**
directly.

It is intentionally narrow:

- one model-specific Q8_0 projector;
- one 256-bit wrapping VNNI operation: `VPDPBUSD ymm`;
- `VPSIGNB(weight, q)` plus precomputed unsigned `abs(q)` for signed × signed;
- four output rows per inner tile;
- eight F32 accumulator lanes per output row;
- the existing fixed LFM reduction tree;
- one contiguous row-range surface for later AP partitioning.

There is no generic GEMM layer, no GPU-style Q8x16 packing, no zero-point
correction, no weight sidecar, no word VNNI, and no saturating VNNI.

## Apply

From the unpacked bundle:

```bash
python3 apply.py /path/to/TRUEOS --check > /tmp/trueos-lumen-cpu-vnni.patch
python3 apply.py /path/to/TRUEOS
```

`--check` runs every source anchor and prints the exact unified diff without
writing. The normal invocation writes six paths:

```text
crates/trueos-lfm25-cpu/src/cpu_vnni.rs       new kernel + tests
crates/trueos-lfm25-cpu/src/lib.rs            exports + model constants
src/r/lfm25_hybrid_cpu_backend.rs             native model + CPU projection
src/lumen/decode.rs                           CPU-VNNI open/checkpoint/restore
src/r/lumen_service.rs                        production Lumen route
src/r/lfm25_boot_warm.rs                      native CPU asset warmup
```

`files/crates/trueos-lfm25-cpu/src/cpu_vnni.rs` is the exact new Rust module.
The remaining existing-source edits are generated by anchored transforms;
`reference/lfm25_boot_warm.cpu_vnni.rs` is included only as a readable example
of one fully transformed integration file.

The transformer is anchored to TRUEOS commit
`02e0e7a8add0fd793d8fd8d5084c0c7e7dc9a3b8`. The two immediately preceding
Lumen-equivalent commits, `b613742bc74946ae04941f039f613affc5221c38` and
`a926b7135be4b8b6381f4e0cd6b5d1288d8db3b8`, are also recognized. A newer
checkout is accepted only when every exact source anchor still matches. Drift
fails closed before any file is written.

## Kernel contract

For every 34-byte weight block and matching activation block:

```text
weight_scale = f32(fp16(weight[0..2]))
activation_scale = f32(fp16(activation[0..2]))
q = activation[2..34] as i8x32
magnitude = abs(q) as u8x32          # precomputed once per project_many()
signed_weight = VPSIGNB(weight[2..34], q)
dot4x8 = VPDPBUSD(0, magnitude, signed_weight)
acc_f32x8 = VFMADDPS(float(dot4x8), weight_scale * activation_scale, acc_f32x8)
```

The eight lanes are reduced only after all K blocks:

```text
a0 = acc0 + acc4    a1 = acc1 + acc5
a2 = acc2 + acc6    a3 = acc3 + acc7
b0 = a0 + a2        b1 = a1 + a3
output = b0 + b1
```

Both activation and model admission reject signed byte `-128`. The sealed
native model is hashed first and then scanned once for this VNNI precondition.
Admission also verifies the fixed 93 tensors, 354,418,688 quantized values,
11,075,584 blocks, and 376,569,856 native Q8 bytes; the hot loop has no
per-weight validation.

One `VPDPBUSD ymm` is issued per native block and output row. Therefore a
K=1024 row is 32 blocks / 1,088 bytes / 32 VNNI instructions, while a K=4608
row is 144 blocks / 4,896 bytes / 144 instructions. Across the fixed 93
projection matrices, one evaluated token accounts for 11,075,584
`VPDPBUSD` instructions before any future row partitioning.

## Lumen integration behavior

- The native model image remains byte-for-byte unchanged after loading.
- `project_many()` validates the same fixed Q8 descriptors, quantizes the input
  once, precomputes magnitudes once, and executes each descriptor on CPU.
- Q/K/V and gate/up still share one activation quantization through the existing
  batch-shaped call.
- Tied token embedding dequantization now reads the native 34-byte rows rather
  than the Q8x16 layout.
- Boot warmup admits AVX2, AVX-VNNI, FMA, and enabled XMM/YMM state, then warms
  the native model and F32 sidecar without issuing a projection.
- Session images keep the existing mutable-state format but bind the model hash
  field to the native image SHA. A checkpoint produced by the packed iGPU path
  therefore fails closed instead of being silently restored under a different
  immutable model layout.
- Existing iGPU kernels and tooling are not deleted; this bundle disconnects
  them only from the production Lumen backend.

## Deliberate non-goals for this pass

The bundle does **not** add AP fan-out, a work-stealing scheduler, NUMA/model
replication policy, row-range calculators, projection fusion, F16C scale
conversion, or benchmark orchestration. `Q8VnniProjector::project_rows()` is the
single future-facing seam: each AP can receive a contiguous output slice without
changing arithmetic or reduction order.

## Validation

Run the independent checks included in the bundle. The Python checks use only
the standard library; the assembly/runtime probes use `clang` by default and
accept another compiler through `CC`:

```bash
./validation/run_validation.sh
```

The prepared result is recorded in `validation/RESULTS.txt`. It covers:

- all 65,025 admitted signed activation/weight pairs;
- random dot4 checks against the old pair-saturating scalar oracle;
- bit-identical F32 lane accumulation and fixed reduction for K=1024 and K=4608;
- quantizer exclusion of activation `-128`;
- the fixed 93-matrix/model byte arithmetic;
- bundle-level checks that reject saturating, word, 128-bit, zero-point, and
  weight-sum-correction paths;
- a compact fixture that exercises every anchored existing-source transform;
- a Clang code-generation probe that requires `VPSIGNB`, `VPDPBUSD`,
  `VCVTDQ2PS`, and `VFMADD` in emitted assembly;
- a CPUID-gated native runtime probe that executes the signed-magnitude dot4
  mapping immediately when the validation host advertises AVX-VNNI.

Then run the repository tests on the target machine:

```bash
cargo test -p trueos-lfm25-cpu --lib
```

The hardware parity tests skip only when AVX-VNNI is unavailable. On the
intended machine they compare every output bit against the existing
`q8_matrix_vector_quantized()` oracle for one-row, four-row, tail-row, K=1024,
and K=4608 cases.

## Validation boundary of this bundle

The preparation environment did not contain a Rust toolchain and its CPU did
not advertise AVX-VNNI, so `cargo test`, rustfmt, and the CPUID-gated runtime
probe could not execute the real instruction here. The Rust implementation
follows the same stable AVX-VNNI intrinsic and CPUID/XCR0 admission pattern
already present in TRUEOS; the independent arithmetic, bundle-consistency, and
emitted-instruction probes passed, while the native runtime probe correctly
reported `SKIP`. The target-machine Cargo and Lumen runs remain the decisive
integration tests.
